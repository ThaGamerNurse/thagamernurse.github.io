Writing

How do you verify 64,000 lines you can't read?

Everyone is focused on getting the model to write good code. The harder question is what you do when it has written a great deal of it and you have no way to check.

Andrew Gaston · 27 July 2026 · 7 min read

I'm a registered nurse. I run operations at a small primary care practice in Philadelphia. Over the last few months I've had AI build an EMR for that practice: about 64,000 lines, 1,657 passing backend tests, FHIR R4, C-CDA, QRDA, X12 835 remittance handling. I also have a trading agent running against a live brokerage account, and five games.

I cannot read any of it. Not really. I can follow a function if I sit with it, but I could not review a pull request and tell you whether it was correct.

That turns out to be the actual problem, and almost nobody talks about it. Here is what I ended up building to answer it. Most of it I arrived at by getting burned.

The thing that doesn't work: reading the summary

Early on I did what everybody does. The model finishes, tells me what it did, and I nod. This fails in a specific and nasty way: the summary is generated by the same process that wrote the code. If it misunderstood the task, the summary will confidently describe the misunderstanding. It is not lying. It genuinely believes it.

You need a check that does not come from the thing being checked.

01Pay someone to disagree

When a review turns up a problem, I don't accept the finding. I hand it to separate agents whose entire job is to disprove it, prompted to default to "refuted" when uncertain. If most of them succeed, the finding gets thrown out.

This sounds like overhead. It is the highest-value thing in the whole setup. A single reviewing agent generates findings that are plausible, well written, and frequently wrong, and if you act on all of them you spend your week fixing imaginary bugs and introducing real ones. Twelve audit rounds on the EMR produced 53 defects that survived refutation. The raw count before refutation was much higher.

It works best when the verifiers get different lenses rather than being three copies of the same skeptic. A security reviewer, a performance reviewer, and someone whose only job is "does this actually reproduce" catch different things.

02Audit by outcome, never by phrase

This one cost me weeks before I understood it.

I gave a correction about when the agent was allowed to sell a position. It updated the rule I pointed at, swept the rest of the rulebook for related wording, and found nothing. Clean, done.

Except a completely different rule, about never averaging down into a falling knife, could starve a position of money just as effectively as the sell rule could. It never used the word "sell." It never used the word "gate." It survived two audits untouched, because both audits searched for the words in my correction rather than the outcome I was trying to prevent.

State the forbidden outcome in one sentence, then find every rule with the power to cause it, whatever vocabulary it uses.

Grepping for the old wording is not the same activity, and never was.

03A correction with no check will be forgotten

Every time I correct something, two things happen in the same session. The rule goes into the file that governs that behavior, and a check gets added that fails if the old behavior ever comes back.

Why the second part exists

I have a locked rule that says no dollar amounts in one of my billing reference files, because a stale fee schedule is worse than no fee schedule. The check for it matched $ followed by a digit. So writing a bare 142.60 with no dollar sign sailed straight through.

The gate had a hole in it for its entire life. I found out by noticing that my own new entries passed when they should have failed. When I fixed it to catch money-shaped numbers, it immediately surfaced a real leak that had been sitting there for weeks.

A gate that has never failed may simply never have been able to.

04Write state down, or every session starts from zero

There's one document that every session reads before it does anything, and writes back to the moment it learns something. Current state, standing decisions, and a log of what went wrong and why.

It fixes two failure modes. The first is obvious: a fresh session re-deriving context you already paid for, or worse, re-litigating a decision you already made.

The second is subtler and much worse. A correction that only lives in a chat log gets overwritten. I once corrected a policy, the correction went into a session note, and four weeks later a different document confidently asserted the opposite version. That wrong version then got baked into an automated routine, which spent every Monday flagging legitimate work as a violation. Roughly a month of compounding error from one correction that never reached a permanent home.

One caveat I learned the hard way: the state document is not evidence. It records what was true when someone wrote it. A single typo in mine, one transposed digit in a billing code, generated a task that ran for eight days before anything checked it against actual claims data and found the code didn't exist.

05Route by cost, in both directions

Mechanical work goes to a small fast model: renames, extraction, formatting, counting, running the test suite and summarizing failures. Work in an established pattern with a clear spec goes to a mid-tier model. Architecture, ambiguous debugging, security invariants, schema changes, and every final review go to the strongest model available.

The part people skip is that it runs both directions. A small model facing a judgment call is supposed to escalate rather than guess. And anything touching money, health data, credentials, or a deployment goes to the top tier regardless of how small the change looks.

The failure that convinced me all of this was necessary

Late in the build, an end-to-end audit found that five services in the EMR had a fallback: when they couldn't determine who performed an action, they defaulted to a hardcoded physician name.

As a log label that's sloppy. But some of those paths wrote to persisted attestations: who signed a note, who authored an addendum, who ordered a test, who reconciled a record. A signature attributed to a specific named doctor who did not sign it is a forgery, and it is indistinguishable in the database from a real one.

No test caught it, because every test passed. The code did exactly what it said. It was correct and it was catastrophic, and it sat there through eleven prior audit rounds that read the code rather than driving the app.

The fix wasn't renaming the constant. There's now a test that scans the whole service layer and fails if any person-shaped actor name reappears anywhere.

Gate the class, not the symptom, because the symptom will come back wearing a different name.

What this doesn't solve

I still can't read the code. Nothing here changes that. What it changes is that I'm no longer relying on my ability to read it.

It's slower than letting the model run. Adversarial verification roughly doubles the cost of a review round. Writing a check for every correction is genuinely tedious. I do it because the alternative failure mode, in a system that will hold real patient charts, isn't a bug.

And it does not make me a software engineer. It makes me someone who built a governance system around a tool, which is a different skill, and one I think a lot more people are about to need.

I want to build the next one with other people.

If any of this is your area, especially if you've taken health software from prototype to certified and deployed, or if you work on agent safety and want to try to break mine, I'd like to hear from you.
